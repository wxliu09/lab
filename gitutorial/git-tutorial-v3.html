00 · 誤解 1 / 2

「Git 就是備份,commit 就是存檔。」

只求存一份的限制不相關的修改混成一個 commit,訊息只寫「update」。

仍然有版本紀錄,但較難理解原因、審查與撤銷其中一件事。問題是改動混雜,不是一天提交幾次。

事實Git 保存快照;好的 commit 讓改動意圖被看見。

用一組相關改動與清楚訊息,說明改了什麼、為什麼改。版本控制有助於回溯與協作,但不能取代完整備份策略。

00 · 誤解 2 / 2

「多個程式專案放同一個 repo 會衝突,拆開才安全。」

例如同一個計畫的後端 API、管理網站、排程程式,各自有程式碼與設定。

常見誤解把「放在一起」當成衝突的原因。

即使程式專案彼此相依、經常一起修改,也因為擔心 conflict 而全部拆開,期待不必再處理整合問題。

事實Git 判斷改動能否整合,不是程式專案的數量。

各自修改不同檔案,通常可自動合併;重疊修改或檔案刪改等情況才可能需要人工判斷。拆開 repo 能隔離部分變更,但不會消除跨專案的相依與整合需求。

Repo 怎麼分,看程式專案的關係與協作需求;不是只看怕不怕衝突。

第 3 章:用程式專案的實例看衝突
講者提示

「程式專案」在這裡是指後端 API、管理網站、排程程式等各自的程式碼與設定,不限定某個 IDE 的專案格式。可由多人分工,也可由一人維護;一人在多條開發線上修改,同樣可能遇到衝突。

不是要求所有程式專案放在一起,也不是否定拆 repo。應考量共用程式、跨專案修改、同步維護、權限隔離與發佈需求。經常一起變更的專案可考慮同 repo;需要獨立存取權限或維護流程時,拆分也可能合理。同 repo 不等於必須一起建置或部署。

01 · 基礎觀念

Git = 分散式 + 版本控制

  • 版本控制:記錄專案隨時間演變的每一步,每一步都能回頭看、比較、還原。
  • 分散式:一般完整 clone 在本地有歷史,不連線也能 commit、看 log、開分支;遠端是大家約定同步的地方。淺層或部分 clone 則有下載範圍限制。

它解決的不是「檔案弄丟怎麼辦」,而是多人、長期開發一定會遇到的問題:

這段程式為什麼長這樣?

git blame + git show:當時的 commit 訊息、作者、一起改的其他檔案。

兩個人同時改同一個專案?

各自在分支上工作;合併時不重疊的部分自動整合,重疊的部分明確標出來。

上線的版本壞了,哪個改動造成的?

git log 看區間、git bisect 二分搜尋、git revert 建立反向修改;仍需確認相依性並測試。

想試一個大改動,不確定會不會採用?

開分支,想做多久做多久;不採用就刪掉,main 從頭到尾乾乾淨淨。

補充

Git 是一個分散式版本控制系統(Distributed Version Control System)。它要解決的問題不是「檔案弄丟怎麼辦」,而是下面這幾個在多人、長期開發時一定會遇到的問題:

  • 這段程式為什麼長這樣?半年後沒人記得。git blame + git show 直接給你當時的 commit 訊息、作者、還有同一次一起改的其他檔案。
  • 兩個人同時改同一個專案怎麼辦?不靠「你先別動,我改完再說」。各自在分支上工作,合併時 Git 自動整合不重疊的部分,重疊的部分明確標出來。
  • 上線的版本壞了,哪一個改動造成的?git log 看區間、git bisect 二分搜尋、git revert 建立反向提交而不改寫既有歷史;後續改動可能依賴被撤銷的內容,仍需測試。
  • 想試一個大改動,但不確定會不會採用?開分支,想做多久做多久;不採用就刪掉,main 從頭到尾乾乾淨淨。

01 · 七個核心概念(1 / 2)

repository · commit · branch · merge

repository儲存庫

保存物件、分支與設定的資料庫;一般工作目錄內由 .git/ 管理。取得專案請用 git clone,不要把手動複製或刪除 .git 當成日常操作。

commit提交

指向一次快照,並記錄說明、作者、時間與 parent。內容改變就會得到不同 hash;既有物件不就地修改,但分支指向的歷史可以被改寫。

branch分支

只是一個指向某個 commit 的可移動指標,不是資料夾複本。開分支就是新增一個名字,幾乎零成本;在分支上 commit,指標就往前移。

merge合併

把另一條線的改動整合進目前分支。目前分支沒有新東西就只把指標往前移(fast-forward);否則以共同祖先為基準做三方比對,產生 merge commit。

補充

repository:一般 repo 的 .git 目錄含物件、refs、index 與設定;worktree 的 .git 也可能是指向共用資料的檔案。clone、備份與手動複製並非同一種操作。

commit:一般提交有一個 parent,初始提交沒有 parent,本課的 merge 有兩個 parent。amend / rebase 建立新 commit,reset 移動指標;內容定址不等於禁止改寫歷史,也不等於驗證作者身分。

branch:只是一個指向某個 commit 的可移動指標,不是資料夾複本。開分支就是新增一個名字,幾乎零成本;在分支上 commit,指標就往前移。

merge:把另一條線的改動整合進目前分支。如果目前分支沒有新東西,只是把指標往前移(fast-forward);否則以共同祖先為基準做三方比對,產生 merge commit。

01 · 七個核心概念(2 / 2)

remote · staging area · HEAD

remote遠端

另一份 repo 的別名,通常叫 origin。origin/main 是本地記錄,不是即時遠端查詢;fetch / pull 會更新它,成功 push 也可能更新對應記錄。

staging area暫存區 / index

「下一個 commit 要包含什麼」的草稿。工作目錄改了十個檔案,可以只把相關的三個 git add 進來 commit。這是讓 commit 保持「一件事」的工具。

HEAD目前位置

你現在站在哪個 commit 上,通常透過分支名稱間接指向(HEAD → main → commit);直接指向 commit 時叫 detached HEAD。log、diff、下一個 commit 的 parent 都以它為準。

補充

remote:origin 是別名,origin/main 是本地 remote-tracking ref。fetch / pull、對應的成功 push 或 IDE 背景 fetch 都可能更新它;status 只比較本地已知位置,顯示 up to date 不代表剛查詢過伺服器。

staging area:「下一個 commit 要包含什麼」的草稿。工作目錄改了十個檔案,可以只把相關的三個 git add 進來 commit,剩下的留給下一個 commit。注意 add 進去的是「當下的內容快照」,add 之後又改了檔案,要再 add 一次。

HEAD:指向「你現在站在哪個 commit 上」,通常透過分支名稱間接指向(HEAD → main → commit)。直接指向 commit 時叫 detached HEAD。git log、git diff、下一個 commit 的 parent 都以 HEAD 為準。

01 · 基礎觀念

版本控制實際帶來什麼

  • 可回溯:找回仍被保留的已提交版本,並從訊息與審查紀錄理解修改背景。
  • 可平行:多人、多功能同時進行,互不干擾,最後有系統地整合。
  • 可審查:每個改動都是可讀的 diff,review 看的是「改了什麼」而不是整份檔案。
  • 可自動化:CI 對每個分支跑測試、tag 對應發佈版本、部署直接指向 commit。

Git、平台、作者與登入,是不同的事

Git ≠ Git 平台

Git 負責本地版本控制;GitHub、GitLab 等平台提供遠端 repo 與存取管理。PR / MR、CI 等功能依平台與設定而異;沒有平台也能在本地 commit。

01 · 安全操作

操作前先確認:我的修改存在哪裡?

狀態 / 操作先做什麼
未追蹤 / 未暫存 / 已暫存先看 git status;用 git diff 看未暫存修改、git diff --staged 看這次要提交的內容。
切分支 / 合併 / rebase 前重要工作先 commit 到自己的分支;短期可 git stash -u 收起含未追蹤檔案的修改,但不含被忽略檔案。
restore / reset --hard / clean可能丟失未提交內容,不是一般「復原鍵」。先確認範圍;clean 的預覽與刪除須使用相同選項。
commit / push 前不要提交密碼、token、正式資料。.gitignore 不會停止追蹤既有檔案,也不會清除歷史;憑證外洩應先撤銷或輪換。

沒有文字衝突 ≠ 整合正確。不同檔案的改動也可能使 API、設定或資料格式不相容;完成整合後仍需測試與 review。

安全邊界

reflog 只記錄本地引用位置,不保存任意未提交內容,而且會過期。被忽略的本機設定與資料,應依公司的備份與機密管理方式保存,不要為了「備份」而加進 Git。

  • 改同一個檔案但不同區域(一個改 import,一個改函式內容)
  • 只有一邊改
  • 兩邊剛好改成一模一樣
容易需要人工處理
  • 兩條開發線把 shared/config.js 同一段設定改成不同值
  • 相鄰的行各自被改(Git 無法確定順序)
  • 一邊改了檔案內容,另一邊把檔案刪了(modify / delete)
  • 大範圍排版與其他內容修改重疊,或雙方改名 / 修改二進位檔

拆 repo 也不會讓相依關係消失。後端 API 改了回傳格式,網站卻沒同步調整,即使沒有 Git 衝突也可能整合失敗;仍需測試。

回看誤解 2:不要因怕衝突就拆 repo
回應開場情境

不同程式專案的例子假設只修改各自檔案,沒有其他重疊改動或檔案結構變更。Git 比較的是共同祖先與雙方改動,不是目錄中有幾個程式專案;也不是只有多人開發才會衝突。

拆 repo 可以隔離部分檔案層級的變更,但共用程式、API 契約與版本相容性仍要管理。自動合併只表示 Git 能整合文字,不代表功能正確;先依程式專案的關係選擇 repo 邊界,再用小而內聚的改動、及早整合與審查降低風險。

03 · 關鍵事實

衝突不會改壞原有 commit

工作目錄會出現待處理內容,暫存區與合併狀態也會改變;原有 commit 仍在,尚未建立最終的 merge commit。

合併尚未完成時可 git merge --abort。合併前先 commit 或 stash 重要修改;帶著未提交內容開始時,Git 不保證能完整恢復。

03 · 小心

rebase 時,ours / theirs 會對調

git rebase main 是「從 main 開始重放你的 commit」:HEAD 是新基底加上已成功重放的內容,>>>>>>> 後面是正在重放的原 commit。

這是「我明明選了 ours 怎麼反了」最常見的原因;git pull --rebase 也一樣。

解決流程(merge 版)

  1. 先確認合併前已保存工作,再看訊息。CONFLICT (content): Merge conflict in config.js 告訴你待處理的檔案。
  2. git status 列出所有 Unmerged paths;這份清單就是待辦事項。
  3. 打開檔案,搜尋 <<<<<<<。每一段決定:留我的、留對方的、兩邊都留、或重寫。不確定就問 —— git log --merge 會列出雙方相關的 commit,作者就在上面。
  4. 整理成最終內容並移除三個標記行。檢查 diff,確認設定符合需求並執行適用測試;沒有標記不等於正確。
  5. git add config.js —— 對衝突檔案來說,add 的意思是「我宣告這個檔案解決了」。
  6. git commit。Git 自動帶 Merge branch 'feature/rate-limit' 訊息,直接存檔即可。這個 merge commit 有兩個 parent,衝突正式結束。
  7. 尚未完成合併而想中止?git merge --abort。已 commit 就不能用它撤銷;不要用 --abort 當成未提交修改的備份。

縮短分岔時間

短命分支 + 頻繁同步 main,及早發現差異。這是經驗法則,不是可保證衝突次數或行數的公式。

04 · 分支策略

分支解決的不只是衝突

  • 隔離:未完成工作可先留在分支;主線是否能跑,仍需要 CI、review 與修復流程保障。
  • 可審查的單位:review 的對象是一個有範圍、有描述的 PR,不是散落在 log 裡的二十個 commit。
  • 可靠的 CI 訊號:CI 對「這個分支」說 pass 或 fail,責任歸屬清楚。
  • 可追蹤的發佈:用 tag / commit 記錄版本。revert 可反向修改程式碼,但資料庫遷移、外部狀態與部署仍需回滾計畫。
  • 不用互相等:沒人需要「等我改完你再動」。平行工作是 Git 的預設,不是特例。
04 · Recommendation

團隊試行建議,不是通用硬性規則

若主要維護單一版本的內部系統,且具備 CI 與 review 能力,可從簡單的短命分支流程開始;先確認 QA 與部署限制。

  1. 可試行 GitHub Flow 式流程:平台支援且計畫採用時,以工作分支 + PR / MR、主線保護與必要檢查協作;實際門檻由各計畫管理員依 協作流程範例 訂定。GitHub Flow 是流程名稱,不限定 GitHub 平台。
  2. 短命分支可先以 1 到 3 天為目標,依工作與風險調整。可行時拆 PR,或以 feature flag 控制未開放功能。
  3. 固定節奏同步 main:在乾淨的工作分支上 git fetch origin 後 git merge origin/main;若選 rebase,先約定歷史改寫規則。
  4. PR 以單一目的與可審查為準;200 / 400 行只作討論參考,不是硬上限。review 等待時間也應列入試行觀察。
  5. 合併後刪分支、發佈打 tag(v2026.09.09 或語意化版本皆可,一致就好)。
  6. 等到需要同時維護多個已發佈版本時,再考慮加 release 分支;不要一開始就上 Git Flow。
04 · 協作流程範例

Push ≠ 已合併 ≠ 已部署

以下適用於平台支援且計畫採用 PR / MR 的情境,不代表公司的每個平台都具備,也不是公司統一強制流程。

  1. Push 工作分支:把本地提交送到 origin 遠端的 feature/login 分支;本地沒提交的內容不會一起上傳。
  2. 建立 PR / MR:確認來源 feature/login、目標 main,描述改動、原因與影響範圍。
  3. 交付審查證據:列出實際完成的測試、尚未確認的風險,指定 reviewer;不要把「準備測試」寫成「測試通過」。
  4. 滿足門檻後合併:檢查、核准、合併方式與權限依該計畫設定;有衝突時先處理。沒有設定 CI 不等於 CI 全部通過。
  5. 依計畫流程發佈:自動 / 人工、測試 / 正式環境與回滾方式另行約定。合併完成不代表已上線,main 也不一定是正式環境版本。

05 · 檔案管理

這些檔案,不要直接列入「一律忽略」

NuGet 與 lockfile

.csproj 裡的 PackageReference 是依賴宣告,必須提交;啟用鎖定模式產生的 packages.lock.json 通常也提交。還原下來的套件(obj/ 內的 project.assets.json、舊式 packages/)重新還原即可,不提交。

Visual Studio 的共用與個人設定

.sln、.csproj、.editorconfig、Directory.Build.props 是團隊共用,要提交;.vs/、*.user、*.suo 是個人視窗、偵錯參數與本機路徑,不提交。VS 建立 repo 時可勾選 .gitignore 範本,既有 repo 要自己補。

appsettings 與 User Secrets

appsettings.json、appsettings.Development.json 可提交,但只放無機密預設值。機密放 User Secrets(專案右鍵「管理使用者密碼」,在使用者目錄)或環境變數;本機覆寫檔不追蹤,只追蹤欄位範本。

產生碼、資產與測試資料

EF Core 的 Migrations/ 與 *.Designer.cs 是來源,要提交;bin/、obj/ 是建置輸出。大型資產視公司政策採 LFS 或資產儲存;測試資料用人工合成內容,正式資料即使改名也不是測試資料。

系統運作時的實體檔案目錄

upload/、dataFiles/、App_Data/ 這類放使用者上傳檔、匯入匯出資料或暫存檔的目錄,內容是運作時資料,不是程式來源:要忽略,並依備份政策另外保存。需要目錄存在時,用 upload/* 加 !upload/.gitkeep 只保留空目錄。

Git LFS 不是機密保護工具,也不會自動移除已進歷史的大檔;*.pubxml 發佈設定檔可能含連線字串,官方範本預設忽略。
