00開場:兩個誤解

在講任何指令之前,先把這兩個想法攤在桌上。它們是大多數「Git 很麻煩」的真正來源。

誤解 1「Git 就是備份,commit 就是存檔。」

結果:一天 commit 一次、訊息寫「update」、所有人都在 main 上改、要找某個改動只能靠記憶。

事實Git 記錄的是「意圖」,不是「檔案狀態」。

每個 commit 回答:改了哪些東西、為什麼改、跟哪些改動是一組的。備份只回答「那時候長什麼樣」。

誤解 2「開分支會製造 conflict,所以大家都直接改 main 最安全。」

結果:誰先 push 誰贏、pull 下來別人的半成品把自己的環境弄壞、release 前夜手動比對檔案。

事實Conflict 不是分支造成的,是「兩個人改同一段程式」造成的。

不開分支只是把衝突從「Git 幫你標出來」變成「悄悄被覆蓋」。分支讓衝突變小、變早、可反悔。

今天的路線01 建立正確的心智模型 → 02 把指令依頻率排好 → 03 親手解一次 conflict,拆掉心理障礙 → 04 選一個適合團隊的分支策略。每一章結尾都有情境測驗,現場可以一起答。

01Git 基礎觀念

Git 是什麼,解決什麼問題

Git 是一個分散式版本控制系統(Distributed Version Control System)。拆開來看:

  • 版本控制:記錄一個專案隨時間演變的每一步,每一步都能回頭看、比較、還原。
  • 分散式:每個人手上都有完整的歷史,不需要連線也能 commit、看 log、開分支;伺服器(GitHub / GitLab)只是大家約定同步的地方。

它要解決的問題不是「檔案弄丟怎麼辦」,而是下面這幾個在多人、長期開發時一定會遇到的問題:

這段程式為什麼長這樣?

半年後沒人記得。git blame + git show 直接給你當時的 commit 訊息、作者、還有同一次一起改的其他檔案。

兩個人同時改同一個專案怎麼辦?

不靠「你先別動,我改完再說」。各自在分支上工作,合併時 Git 自動整合不重疊的部分,重疊的部分明確標出來。

上線的版本壞了,哪一個改動造成的?

git log 看區間、git bisect 二分搜尋、git revert 精準撤銷那一個改動而不影響其他人的東西。

想試一個大改動,但不確定會不會採用?

開分支,想做多久做多久;不採用就刪掉,main 從頭到尾乾乾淨淨。

備份 vs 版本控制:本質差在哪

「備份」保存的是某個時間點的檔案狀態;Git 保存的是一連串有意圖的變更。這個差別決定了你能用它做什麼。

面向備份(複製資料夾 / 雲端硬碟 / zip)Git
單位整個資料夾的快照,沒有語意一個 commit = 一組有目的的改動 + 說明 + 作者 + 時間 + 前一個版本
回答的問題「上週三長什麼樣?」「這行是誰、為什麼改的?」「這個 bug 是哪次改動引入的?」
還原粒度整包還原,順便把別人的東西也覆蓋掉可以只撤銷某一個 commit、某一個檔案、甚至某幾行
多人協作final_v2_真的最終版(3).zip各自分支、自動合併、衝突明確標記、有紀錄的 code review
平行嘗試再複製一份資料夾git switch -c try-new-api,零成本,隨時切換
儲存每份都是完整複本內容定址,相同內容只存一次;歷史就是一張 commit 的圖
所以「一天 commit 一次」為什麼不好?因為一個 commit 混了十件事,等於退回備份:不能只撤銷其中一件、看不出哪個改動造成問題、review 的人要一次讀完全部。一個 commit 做一件事,訊息寫「為什麼」,是所有後面工具(blame、bisect、revert、cherry-pick)能發揮作用的前提。

七個核心概念

先建立心智模型,指令只是操作這些東西的動詞。下面每一項都會在練習場裡看到對應的視覺化。

repository儲存庫

專案目錄裡的 .git/ 資料夾,裝著全部歷史(commit 物件)與所有指標(branch、tag、HEAD)。刪掉它,Git 就忘了一切;複製它,就是一份完整的 clone。

commit提交

一次快照 + 說明 + 作者 + 時間 + parent 指標。有 parent 指標,commit 才串成歷史;merge commit 有兩個 parent。每個 commit 由內容算出的 hash 識別,內容一改 hash 就變,所以歷史不可竄改。

branch分支

只是一個指向某個 commit 的可移動指標,不是資料夾複本。開分支就是新增一個名字,幾乎零成本;在分支上 commit,指標就往前移。

merge合併

把另一條線的改動整合進目前分支。如果目前分支沒有新東西,只是把指標往前移(fast-forward);否則以共同祖先為基準做三方比對,產生 merge commit。

remote遠端

另一份 repo 的別名,通常叫 origin。origin/main 是「上次同步時遠端 main 在哪」的本地紀錄,不會自己更新,要靠 fetch / pull。

staging area暫存區 / index

「下一個 commit 要包含什麼」的草稿。工作目錄改了十個檔案,可以只把相關的三個 git add 進來 commit,剩下的留給下一個 commit。這是讓 commit 保持「一件事」的工具。

HEAD目前位置

指向「你現在站在哪個 commit 上」,通常透過分支名稱間接指向(HEAD → main → commit)。直接指向 commit 時叫 detached HEAD。git log、git diff、下一個 commit 的 parent 都以 HEAD 為準。

三個區域:每個檔案改動都走這條路

Working Directory工作目錄:你實際編輯的檔案
→git add
Staging Area暫存區:下一個 commit 的內容
→git commit
Repository.git/:永久的 commit 歷史
→git push
Remoteorigin:團隊共用的 repo

反方向也有對應的指令:git restore 把工作目錄改回暫存區的版本、git restore --staged 把檔案從暫存區移出、git reset 移動分支指標、git fetch / git pull 把遠端的東西拿回來。搞懂一個指令在哪兩個區域之間搬東西,就不會用錯。

檔案狀態意思git status 顯示為
untrackedGit 完全不認識這個檔案,從沒 add 過Untracked files(紅)
modified已追蹤,工作目錄的內容和暫存區不同Changes not staged for commit(紅)
staged已放進暫存區,和 HEAD 的版本不同Changes to be committed(綠)
clean / committed三個區域內容一致nothing to commit, working tree clean

版本控制實際帶來什麼

  • 可回溯:任何時間點的任何檔案都拿得回來,而且知道是誰、為什麼改。
  • 可平行:多人、多功能同時進行,互不干擾,最後有系統地整合。
  • 可審查:每個改動都是可讀的 diff,review 看的是「改了什麼」而不是整份檔案。
  • 可自動化:CI 對每個分支跑測試、tag 對應發佈版本、部署直接指向 commit。
  • 可放心實驗:做壞了 git restore、git reset、git reflog 都能救;commit 過的東西幾乎不可能真的弄丟。

練習場 A:從零開始建立一個 repo

目標:親手走一次「建立 repo → 建檔案 → 加入暫存區 → commit → 開分支 → 合併」。右邊的三個區域面板會隨每個指令變化,commit 樹會在第一個 commit 出現後長出來。點下方的指令卡片會填入輸入框,按 Enter 執行。

03Conflict 處理實戰

Conflict 是 Git 在說:「這裡有兩個合理的版本,我不敢替你決定。」它不是錯誤、不會弄壞任何東西、而且隨時可以反悔。這一章的目標是讓你解過一次之後,再看到 CONFLICT 只會覺得「喔,又來了,兩分鐘」。

為什麼會發生:三方合併

Git 合併兩條線時不是「比較 A 和 B」,而是找出兩者的共同祖先(merge base),然後分別看「A 相對祖先改了什麼」和「B 相對祖先改了什麼」。這叫三方合併(3-way merge)。

衝突的必要條件:同一個檔案、同一段(或相鄰)的行、自從分岔之後兩邊都改了、而且改得不一樣。少一個條件都不會衝突。
不會衝突的情況
  • 兩個人改不同檔案
  • 改同一個檔案但不同區域(一個改 import,一個改函式內容)
  • 只有一邊改
  • 兩邊剛好改成一模一樣
會衝突的情況
  • 兩邊都改了同一行(最常見:設定值、版本號、同一個函式簽章)
  • 相鄰的行各自被改(Git 無法確定順序)
  • 一邊改了檔案內容,另一邊把檔案刪了(modify/delete)
  • 一邊改了整個檔案的排版(縮排、換行)—— 這是自找的
關鍵事實衝突只存在於你的工作目錄。合併還沒 commit 之前,repo 裡沒有任何東西被改變;同事的 commit、你的 commit 都原封不動。最壞情況就是 git merge --abort 回到合併前。

解讀衝突標記

發生衝突時,Git 會把兩個版本一起寫進檔案,用三種標記分隔。以 config.js 為例:

// config.js(衝突發生時的樣子)
module.exports = {
  appName: 'orders-api',
<<<<<<< HEAD                       ← 從這裡到 ======= 是「你這邊」(HEAD,目前分支)的版本
  maxConnections: 50,
=======                           ← 分隔線
  maxConnections: 200,
  poolTimeoutMs: 3000,
>>>>>>> feature/rate-limit          ← 從 ======= 到這裡是「對方」(被合併進來的分支)的版本
  logLevel: 'info',
};
標記意思備註
<<<<<<< HEAD「ours」區段開始:你目前所在分支的內容做 git merge 時,HEAD 就是你的分支
=======兩個版本的分隔線標記外面的行(例如 appName)沒有衝突,Git 已經處理好
>>>>>>> feature/rate-limit「theirs」區段結束:被合併進來那一邊的內容後面的名字告訴你另一邊是誰
rebase 時兩邊會對調git rebase main 是「站在 main 上重放你的 commit」,所以此時 HEAD 是 main 的內容,>>>>>>> 後面是你自己的 commit。這是最常見的「我明明選了 ours 怎麼反了」的原因。git pull --rebase 也一樣。

解決衝突就是把整段(含三個標記行)換成你要的最終內容。可以是任一邊、兩邊都留、或重寫。上面的例子,合理的結果大概是:

module.exports = {
  appName: 'orders-api',
  maxConnections: 200,       ← 採用對方的新值(問過同事:rate-limit 需要更多連線)
  poolTimeoutMs: 3000,
  logLevel: 'info',
};

解決流程(merge 版)

  1. 看訊息,不要關掉。CONFLICT (content): Merge conflict in config.js 已經告訴你哪個檔案。通常只有一、兩個。
  2. git status 列出所有 Unmerged paths;這份清單就是待辦事項。
  3. 打開檔案,搜尋 <<<<<<<。每一段決定:留我的、留對方的、兩邊都留、或重寫。不確定就問 —— git log --merge 會列出雙方相關的 commit,作者就在上面。
  4. 刪掉三個標記行,確認檔案能跑(編譯、測試、至少開起來看一眼)。IDE 的 Accept Current / Incoming / Both 按鈕做的就是這件事。
  5. git add config.js —— 對衝突檔案來說,add 的意思是「我宣告這個檔案解決了」。
  6. git commit。Git 會自動帶 Merge branch 'feature/rate-limit' 訊息,直接存檔即可。這個 merge commit 有兩個 parent,衝突正式結束。
  7. 反悔?任何時候 git merge --abort,回到合併前的狀態,什麼都沒發生。
rebase 版的差別

步驟 5 之後不是 git commit,而是 git rebase --continue;放棄用 git rebase --abort。因為 rebase 是一個一個 commit 重放,可能要解好幾次(每個 commit 一次)。

整檔二選一的捷徑

整個檔案都要某一邊時:git checkout --ours config.js 或 git checkout --theirs config.js,再 git add。適合 lock file、產生出來的檔案;手寫程式碼還是逐段看比較安全。

練習場 C:親手解一次

情境:你在 main 上把 config.js 的連線數改成 50 並 commit;同事的 feature/rate-limit 分支把同一行改成 200 還多加了一個設定。現在要把 feature 分支合併進 main。用 edit config.js 會開啟編輯器(有「保留我的 / 保留對方 / 兩邊都留」的快速鍵),右側任務清單會自動打勾。

PLAYGROUND C — merge conflict scenario

讓衝突變少、變小的習慣

1. 小 commit、小 PR

改動越小,和別人重疊的機率越低,就算衝突也一眼看得完。一個 PR 超過 400 行就該想辦法拆。

2. 常常整合

每天把 main 併進(或 rebase 到)你的分支。分岔兩小時的衝突是兩行,分岔兩週的衝突是兩百行。

3. 分支活得短

功能太大做不完?拆成可以獨立合併的幾段,用 feature flag 藏起來。分支的壽命是衝突大小的主因。

4. 排版和重構分開 commit

整檔 reformat 會和所有人衝突。要做就單獨一個 commit、先講一聲、挑沒人在改的時候合併。

5. 產生出來的檔案不要手動解

lock file、build 產物、snapshot:選一邊然後重新產生(npm install 之類),不要逐行比對。

6. 共用檔案先講

config、route 表、i18n 字串檔、DI 註冊:這些是衝突熱點,動之前在群組講一聲,或設計成每個功能一個檔案。

給害怕的人統計一下你會發現:真正的衝突一週可能一兩次、每次一兩個檔案、每個檔案幾行。相比之下,「不開分支直接改 main」帶來的是每天都在處理別人半成品的成本,而且那些問題 Git 不會幫你標出來。

情境測驗:衝突篇

04分支策略

「策略」聽起來很大,其實只是回答三個問題:main 代表什麼?功能在哪裡開發?什麼時候、怎麼合回去?選一個全隊都照做的答案,比選哪一個更重要。

分支不是成本,分岔的時間才是

先拆掉「開分支 = 麻煩」這個印象。在 Git 裡,分支是一個 41 bytes 的檔案,裡面寫著一個 commit hash。建立、切換、刪除都是毫秒等級。真正有成本的是「兩條線分開多久、各自改了多少」——這件事不管你有沒有開分支都存在。

情境所有人直接改 main各自開短命分支
同事改壞了東西你 pull 下來就一起壞,只能等他修他的分支壞他的,main 永遠是能跑的版本
兩人改同一段後 push 的人被拒絕,匆忙 pull 後在自己的環境裡解衝突,沒人 reviewPR 上看得到衝突,可以一起看、一起決定
做到一半要改急件手上的半成品不知道往哪放(stash 堆成山)commit 在 feature 分支,切到 main 開 hotfix 分支,五秒
Code review沒有明確的 review 單位,只能整段 log 看一個 PR = 一個可 review、可討論、可 CI 的單位
某功能決定不做了要從 main 上把相關 commit 一個個 revert刪分支,main 乾乾淨淨
發佈「現在 main 上有哪些東西是完成的?」沒人確定merge 進 main 的就是完成的,tag 一下就是版本

常見策略比較

以下三張圖都是用本頁的模擬引擎產生的,和練習場的圖是同一種畫法:圓點是 commit、標籤是分支指標、有兩個 parent 的是 merge commit。

1. Trunk-Based Development(主幹開發)

規則
  • 只有一條長期分支 main(trunk)
  • 每個改動開極短命的分支(小時到一兩天),PR 通過 CI 就併回
  • 沒做完的功能用 feature flag 關起來,一樣可以合併
  • 發佈直接從 main 上 tag,必要時開 release 分支只收 hotfix
適合 / 不適合
  • ✔ CI 完善、測試可信、團隊紀律好、持續部署
  • ✔ 想把衝突壓到最小的團隊(分岔時間最短)
  • ✘ 沒有自動化測試:main 會常常壞
  • ✘ 需要同時維護多個已發佈版本

2. GitHub Flow

規則
  • main 永遠可部署
  • 任何工作都從 main 開分支,名字要有意義(feature/order-export、fix/login-timeout)
  • 開 PR 討論、review、跑 CI;通過後合併回 main,刪除分支
  • 合併後就部署(或很快部署)
適合 / 不適合
  • ✔ 大多數 web / 內部系統團隊的預設選擇
  • ✔ 想要 code review 流程但不想管太多分支
  • ✔ 分支壽命建議控制在 1 到 3 天
  • ✘ 需要「這個版本先凍結測試兩週」的流程

3. Git Flow

規則
  • 兩條長期分支:main(只放已發佈版本)與 develop(整合中)
  • feature/* 從 develop 開、併回 develop
  • 準備發佈時從 develop 開 release/x.y,只修 bug,完成後同時併回 main(打 tag)和 develop
  • 線上緊急修正開 hotfix/*,從 main 開,併回 main 和 develop
適合 / 不適合
  • ✔ 有明確版本號、需要同時維護多個已發佈版本(套件、桌面軟體、對外 SDK)
  • ✔ 有獨立 QA 階段的發佈節奏
  • ✘ 持續部署的服務:develop 和 main 的雙軌只是增加合併次數
  • ✘ 小團隊:規則多、容易忘記併回 develop 而漏掉 hotfix

為何良好的分支設計會降低協作成本

衝突的期望大小大約正比於 分岔時間 × 重疊範圍。分支策略能動的就是這兩個變數:

縮短分岔時間

短命分支 + 每天同步 main。兩個人同時改一個檔案的機會沒變,但改動量從兩週縮到一天,衝突從一頁縮到幾行。

縮小重疊範圍

一個分支只做一件事、一個 PR 只碰相關檔案。附帶的 reformat、順手重構、無關的 rename 都是重疊範圍的放大器。

把衝突移到看得見的地方

PR 上的衝突有 diff、有 CI、有兩個人一起看。直接 push main 的衝突發生在某人的機器上,五分鐘內草率解掉,沒人知道。

此外,分支設計還在解「衝突」以外的成本:

  • 隔離:main 永遠能跑。新人 clone 下來就能開發,不用先問「現在 main 是不是壞的」。
  • 可審查的單位:review 的對象是一個有範圍、有描述的 PR,不是散落在 log 裡的二十個 commit。
  • 可靠的 CI 訊號:CI 對「這個分支」說 pass 或 fail,責任歸屬清楚。
  • 可回滾的發佈:merge commit 或 tag 就是發佈單位,出事 revert 一個 merge commit 就撤掉整個功能。
  • 不用互相等:沒人需要「等我改完你再動」。平行工作是 Git 的預設,不是特例。

對我們團隊的建議

RECOMMENDATION
  1. 採用 GitHub Flow:main 受保護(只能經由 PR 合併、CI 必須通過),所有改動走 feature/*、fix/* 分支。
  2. 分支壽命上限 3 天。做不完就拆 PR,或用 feature flag 先合併關閉的程式碼。
  3. 每天早上同步 main:git switch main && git pull && git switch - && git merge main(或 rebase,團隊選一個)。
  4. PR 目標 200 行以內,上限 400 行;review 在一個工作天內完成。
  5. 合併後刪分支、發佈打 tag(v2026.09.09 或語意化版本皆可,一致就好)。
  6. 等到需要同時維護多個已發佈版本時,再考慮加 release 分支;不要一開始就上 Git Flow。
