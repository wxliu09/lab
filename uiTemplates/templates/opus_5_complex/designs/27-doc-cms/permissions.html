權限與角色

墨庫的權限是一張格：六個基礎角色沿一條繼承鏈遞增，稽核員則自檢視者旁分出獨立支線。點選格圖上的任一角色，下方能力矩陣會標出該角色的欄位。

繼承鏈上的角色為嚴格包含關係：審核者必然具備編輯者的一切能力。稽核員是刻意的例外——它只讀，卻能跨知識庫讀，因此不放在主鏈上，避免有人誤以為「升級成管理員就自動含稽核權」。

    自訂角色 Custom Roles — 以能力清單組合，不可繼承

    建立方式

    自訂角色不參與繼承格，它只是一張明確的能力清單。這是刻意的限制：一旦允許自訂角色互相繼承，稽核時就無法在單一畫面判斷某人到底能做什麼。

    1. 於「團隊 → 角色」按下「建立自訂角色」，命名建議用職務而非權限描述。
    2. 逐項勾選能力。系統會即時提示互斥組合，例如勾了「核可發布」卻沒勾「讀取草稿」。
    3. 設定生效範圍：整個工作區、指定知識庫，或指定標籤。
    4. 選填自動到期日。專案型角色建議一律設 90 天，到期前 7 天會通知設定者。
    5. 建立動作寫入稽核日誌，型別為 permission.grant。
    互斥檢查 「變更保存策略」與「批次匯出」不可同時授予非擁有者角色。同時具備這兩項的帳號，可以先縮短稽核保存期再匯出，形成無痕的資料外攜路徑。

    範例定義

    以下為目前生效的「合約審閱者」定義，可由 GET /v1/roles/role_contract_reviewer 取得。

    // 自訂角色 — 合約審閱者
{
  "id":        "role_contract_reviewer",
  "name":      "合約審閱者",
  "scope": {
    "space":   "kb_legal",
    "tag":     "contract"
  },
  "capabilities": [
    "doc.read_published",
    "doc.read_draft",
    "comment.create",
    "comment.resolve_own"
  ],
  "denied": [
    "export.bulk",
    "doc.edit_block"
  ],
  "members":   8,
  "expires_at": "2025-09-02T00:00:00Z"
}
    拒絕優先 denied 永遠勝過 capabilities，也勝過使用者透過基礎角色取得的能力。一位同時是編輯者與合約審閱者的同仁，在 kb_legal 的 contract 標籤下仍然不能編輯區塊。
