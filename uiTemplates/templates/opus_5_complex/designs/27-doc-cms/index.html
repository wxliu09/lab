版本控制機制

墨庫的每一次儲存都是一次不可變的快照。本章說明快照的建立時機、差異計算方式，以及在多人協作時如何以分支與合併維持內容一致性。

設計原則

知識庫的內容不同於程式碼：段落順序頻繁調動、表格與圖片並存、且多數編輯者不熟悉指令列工具。因此墨庫採取 「以區塊為單位的不可變快照」 而非逐行差異，讓合併語意更貼近寫作行為本身。

每個文件由一連串 block 組成，每個 block 擁有穩定的 block_id。移動段落只會改變順序陣列，不會產生刪除／新增的假差異，這是與傳統 diff 工具最根本的分歧。

設計筆記 區塊識別碼在建立後永不重複使用。即使區塊被刪除，其 id 仍保留於歷史快照中，以確保任意時間點都能完整重建文件。

快照與差異

編輯者停止輸入超過 2000ms，或主動按下儲存時，系統建立一次快照。快照僅記錄異動的區塊內容，其餘沿用前一版指標，因此儲存成本與文件長度無關，只與異動量相關。

// 快照結構（簡化）
{
  "snapshot_id": "snap_01HZ8K4Q",
  "parent":      "snap_01HZ8J9M",
  "order":       ["blk_a1", "blk_c9", "blk_b3"],
  "changed": {
    "blk_c9": { "type": "paragraph", "text": "……" }
  },
  "author":      "u_8842",
  "created_at":  "2025-06-08T14:22:07Z"
}

圖 2.1 — 快照僅攜帶異動區塊，其餘以父快照指標繼承

差異呈現

介面層將兩份快照的 order 與 changed 做三向比對，產生四類標記：新增、刪除、修改、移動。移動被獨立標記是刻意的設計——多數協作衝突其實只是段落順序調整。

標記觸發條件合併策略
新增目標存在、來源不存在的 block_id自動併入
刪除來源存在、目標不存在自動併入（除非同時被修改）
修改同一 block_id 內容雜湊不同三向合併，失敗則標記衝突
移動內容相同但 order 索引改變以最後寫入者為準

分支策略

每個文件預設只有 main 一條線。當編輯者需要進行大幅改寫時，可建立具名草稿分支，審核通過後再合併回主線。分支不是必要的——超過八成的日常編輯直接發生在主線上。

  1. 在文件右上角選擇「建立草稿分支」，命名建議使用 提案/主題 格式。
  2. 分支期間主線的更新會即時顯示於側欄提示，可隨時按下「同步上游」。
  3. 送出審核後進入工作流，指定審核者收到通知。
  4. 審核通過即自動合併；若期間主線有衝突區塊，系統會要求人工裁決。
注意 分支存活超過 30 天將自動標記為停滯，並於側欄以灰階顯示。長期分支的合併衝突率會顯著上升，建議拆成多個小型提案。
「版本控制不是為了記錄每一次改動，而是為了讓人敢於改動。」
— 內部設計評審紀要，2024 年 11 月

衝突解決

當同一區塊在兩條線上被不同人修改，系統不會擅自選擇。介面會並列呈現雙方版本與共同祖先，編輯者可逐塊選擇保留哪一側，或直接手動改寫成第三種版本。

所有裁決都會寫入稽核日誌，包含裁決者、時間戳與被捨棄的內容雜湊——被捨棄的內容永遠可以透過 GET /snapshots/{id} 取回。
